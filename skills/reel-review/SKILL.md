# 쇼릴 검토 절차

검토의 목적은 "보는 사람이 틀린 정보를 가져가거나, 읽지 못하고 지나가는 일"을 막는 것이다. 미감 의견은 그다음이다.

## 0. 시각 기준

이 문서의 모든 시각은 **전역 시각**(영상 시작부터의 초, HUD 타임코드)이다. `render.js`의 `--times`와 `audit` 출력도 전역 시각이다. `reel.js`의 장면 함수는 **장면 로컬 시각** t를 쓰고, 효과음 큐는 `at(i, lt) = SC[i] + lt`로 전역 시각을 만든다. 수정 목록에는 "27.6s(전역) / s6 로컬 1.2s"처럼 둘 다 적어 구현자가 바로 찾게 한다.

## 1. 준비

1. `_work/01_storyboard.md`(승인본)와 `_work/02_build_log.md`를 읽는다.
   - **스토리보드가 없는 쇼릴**(하네스 이전에 만든 것 등): `reel.js`의 문자열과 `_work/meta.json`의 `source`를 기준으로 삼고, 원자료와 직접 대조한다. 사실 대조표의 "스토리보드 표기" 열에는 "(없음)"을 적고, 머리에 "스토리보드 없이 검토"라고 밝힌다.
2. 원자료 경로를 확인한다(스토리보드 머리 또는 `meta.json`의 `source`). PDF는 Read 도구로 바로 읽는다(10쪽이 넘으면 `pages` 인자로 나눠 읽는다).
3. 이전 라운드 검토 파일(`_work/03_review_r{n-1}.md`)이 있으면 읽고, 지난 must 항목이 고쳐졌는지부터 확인한다.

## 2. 자동 검사

```
node showreel/tools/render.js audit showreel/reels/{slug}
```

| 종류 | 뜻 | 기본 심각도 |
| --- | --- | --- |
| `offscreen` | 글자 상자가 화면 밖으로 0.45초 이상 나감 | must |
| `margin` | 가장자리 48px 안으로 들어감(HUD와 부딪힐 수 있음) | should |
| `overlap` | 서로 다른 문구가 0.45초 이상 겹침 | 프레임을 보고 판단(판독 불가면 must) |
| `reading-critical` | 필요 읽기 시간의 절반도 안 보임 | 핵심 문장이면 must, 장식이면 should |
| `reading-tight` | 필요 시간보다 조금 짧음 | should(핵심 문장), could(장식) |

자동 검사는 글자 상자만 본다. 그림 요소끼리의 겹침, 색 대비, 탁한 색은 프레임을 봐야 안다. 각 문제에는 전역 시각 구간(`from–to`)과 장면 번호·이름이 붙어 있으니, 그 구간 안의 시각으로 프레임을 뽑아 확인한다.

## 3. 프레임 확인

1. 스토리보드의 장면마다 "핵심 순간"을 고른다. 각 요소가 다 등장한 직후, 강조 사건(도장, 예외, 추천)이 일어난 직후, 장면이 끝나기 직전이다.
2. 전체 훑어보기: 3열 시트(칸당 640×360). 컷 수 제한은 없지만 15컷 안팎이 한 번에 보기 좋다.
   `node showreel/tools/render.js sheet showreel/reels/{slug} --times 1.4,2.6,5.0,... --out showreel/reels/{slug}/build/review_r{n}.png`
3. 작은 글씨(30px 이하)는 3열 시트에서 읽을 수 없다. `--cols 2`(칸당 960×540)나 원본 해상도 `frames`로 다시 본다.
   `node showreel/tools/render.js frames showreel/reels/{slug} --times 21.7,27.6`
4. Read 도구로 이미지를 보고 아래 점검표를 적용한다.

### 점검표
- [ ] 글자가 잘리거나 다른 요소에 가려지지 않는다
- [ ] 한 장면의 요소가 같은 왼쪽 기준선(x 160)과 글자 크기 단계에 맞는다
- [ ] 강조색이 한 장면에 한 곳에만 쓰였고, 경고색(빨강)의 의미가 영상 전체에서 하나다
- [ ] 포화된 바탕 위에 반투명 색이 겹쳐 탁한 색이 나오지 않는다
- [ ] 차트는 한 척도로 그렸고, 눈금 값과 막대 길이가 맞는다
- [ ] 장면 전환 직후(와이프 끝, 약 0.22초) 무언가 움직이고 있다
- [ ] 엔딩 카드가 1초 이상 정지 상태로 머문다
- [ ] **완성 화면(발표 모드 정지 화면)**: `sheet --holds --cols 2`로 장면별 정지 화면을 모아 본다. 각 장면이 슬라이드 한 장으로 성립하는지, 즉 핵심 요소가 다 보이고 등장 중이거나 퇴장 중인 요소가 없는지 확인한다. 등장이 덜 끝났으면 must다

## 4. 사실 대조

화면에 나오는 모든 숫자, 고유명사, 주장 문장을 표로 만든다.

| 시각 | 화면 표기 | 스토리보드 표기 | 원자료 표기·위치 | 일치 |
| --- | --- | --- | --- | --- |

- 문구는 `reel.js`에서 문자열을 찾아(Grep) 정확히 옮긴다. 프레임 이미지에서 읽지 않는다. 작은 글씨를 잘못 읽을 수 있다.
- 스토리보드와 다르면 must(구현 오류). 스토리보드와 원자료가 다르면 must(스토리보드 오류)이며, 수정 대상을 "스토리보드"로 적는다.
- 반올림, 단위, 날짜 표기 차이도 적는다.
- **사실 주장과 연출을 구분한다.**
  - 사실 주장: 시청자가 "원자료가 그렇게 말했다"고 받아들일 문장과 라벨. 수치, 연도, 출처 표기, 검정 방식 같은 방법 설명, "추천", "확정"처럼 결론의 강도를 나타내는 말이 여기에 든다. 원자료에서 찾을 수 없으면 must다.
  - 연출: 분위기를 위한 가상 값. 예시용 위치 코드, 티커의 주문 번호, 장식용 바코드 같은 것이다. 스토리보드의 「연출용 가상 값」 목록에 있거나 누가 봐도 예시면 could 이하로 둔다. 목록에 없는데 사실처럼 보이면 should로 올리고, 스토리보드에 연출로 명시하라고 적는다.

## 4-1. 발표 대본 대조

스토리보드의 장면별 발표 대본을 확인한다.
- 대본의 수치·주장이 화면·원자료와 같은가(다르면 must, 대상 "스토리보드")
- 대본의 말하기 시간(공백 제외 글자 수 ÷ 6초)이 장면 길이 안에 들어가는가(넘치면 should)
- 대본이 화면 문구를 그대로 읽기만 하지 않는가(could)

## 5. 소리 대조

`reel.js`의 `cues`와 장면 코드를 대조한다.
- 도장, 카운터, 예외, 엔딩 같은 주요 사건에 큐가 있는가
- 큐 시각이 장면 코드의 상수에서 계산되는가(숫자를 직접 적었으면 should)
- `end` 큐가 엔딩 타이틀 등장과 맞는가
- 2분짜리라면 막마다 음악 구간 스타일이나 코드 진행이 바뀌는가(한 편곡이 1분 넘게 이어지면 should)
- `drops`는 `hits` 또는 `booms`와 짝을 이루는가

음악을 직접 들을 수 없으면 `audio --out showreel/reels/{slug}/build/check.mp3`로 오류 없이 생성되는지만 확인하고 "청취 확인 필요"를 적는다. `--out` 없이 실행하면 게시용 `reel-music.mp3`를 덮어쓰므로 검토자는 반드시 `--out`을 쓴다.

## 5-1. 타이밍 수정안 쓰는 법

읽기 시간 문제를 고치는 방법은 세 가지다. 앞의 것일수록 영향 범위가 작다.
1. **장면 안에서 등장을 앞당긴다**: 해당 `rise`/`typeOn`의 시작 시각(로컬)을 줄인다. 다른 장면에 영향이 없다.
2. **문구를 줄인다**: 필요 시간이 줄어든다. 문구는 사실 대조를 다시 해야 하므로 수정 대상을 "스토리보드"로도 적는다.
3. **장면 경계를 옮기거나 전체 길이를 늘린다**: `reel.js`의 `SC` 배열 하나만 바꾸면 장면 표, `at()`로 계산한 큐, 음악(장면 구간을 따라감)이 함께 움직인다. 추가로 바꿀 곳은 `meta.dur`(= SC 마지막 값)와 `meta.poster`다. 큐를 숫자로 직접 적은 곳이 있으면 목록에 따로 적는다.

수정안에는 바꿀 값을 "이전 → 이후"로 적되, 최종 확인은 구현자가 `audit`을 다시 돌려 한다고 적는다.

## 5-2. 숏동영상(3~5분, 자막형) 추가 점검

스토리보드가 숏동영상 모드면 다음을 더 본다. 기준은 `reel-storyboard/references/explainer-mode.md`다.

- **범위 나누기**: 한 번에 5분을 다 보지 않는다. 장(챕터)마다 비트 시각으로 시트 한 장씩 뽑는다(`--times` 15컷 안팎). 완성 화면은 `sheet --holds --cols 4`.
- **자막**: 스토리보드 「자막 전체」와 화면 자막을 한 줄씩 대조한다(문자열, 표시 구간). 표시 시간이 0.6 + 글자 수/8 + 0.4초보다 짧으면 should, 절반도 안 되면 must. 자막 띠(y 890~985)가 그림이나 다른 글자를 가리면 must.
- **처음 보는 사람 기준**: 용어가 정의(그림)보다 먼저 나오면 should. 한 장면에 새 개념이 둘 이상이면 could.
- **WHY·WHAT 범위**: 구현·알고리즘 설명이 들어가 있으면 should(사용자가 요청한 경우 제외).
- **목표와 결과 구분**: 아직 만들지 않은 해결책의 효과가 결과처럼 표시되거나("줄었다", "개선됐다") 원자료에 없는 개선 수치가 있으면 must.
- **확인 수준**: 원자료가 "업체 설명"·"미확인"으로 표시한 내용을 화면이 단정하면 must.
- **리듬**: 30~40초 넘게 "순간"(큰 숫자, 도장, 반전) 없이 같은 밀도가 이어지는 구간을 could로 적는다.
- **소리**: 자막 구간에 드럼이 강한 스타일(`drive`, `chorus`)이 오래 이어지면 could. 5분짜리 `audio --out build/check.mp3`는 수십 초 걸린다.

## 6. 출력 (`_work/03_review_r{n}.md`)

```markdown
# 검토 r{n} — {slug}
- 판정: pass | fix
- 요약: must {a} · should {b} · could {c}
- audit: {종류별 건수}
- 확인한 프레임: {시각 목록} → build/review_r{n}.png

## 수정 목록
| # | 심각도 | 시각·장면 | 문제 | 고칠 방법 (파일·함수·값) | 대상 |
| --- | --- | --- | --- | --- | --- |
| 1 | must | 27.6s(전역) / s6 로컬 1.2s | "하루 1회 미만이면…"이 0.7초만 보임 | s6의 퇴장 시작 1.85→2.6, 엔딩 요소 등장 +0.75초(SC 끝을 30→30.8로, meta.dur도) | reel.js |

## 사실 대조표
## 지난 라운드 항목 확인
## 좋았던 점 (유지할 것)
```

판정 기준:
- must가 0건이면 `pass`. should만 남았으면 `pass`로 하고 목록에 남긴다.
- must가 1건 이상이면 `fix`.

"고칠 방법"은 구현자가 바로 실행할 수 있게 쓴다. "더 읽기 쉽게"가 아니라 "s6에서 조건 문장 등장 1.25 → 0.9, 퇴장 1.85 → 2.6"처럼 쓴다.
